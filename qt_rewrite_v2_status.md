# ColorizingDMD Qt Rewrite v2 — Working Status

Snapshot of where the rewrite stands, written 2026-10-13 so work can resume after a break.
`qt_rewrite_v2_plan.md` is the original plan; `Handbook.md` is the user-facing behaviour reference
and is kept current with every change. This file records decisions, state and open work that
neither of those holds.

## Ground rules decided by the owner

- **Compatibility target is the Win32 editor 3.17.3 only.** Nobody has used a Qt build yet, so
  files written by earlier Qt builds (v2 or the first `qt_playback_wip` attempt) need no support
  and no repair code.
- **libserum is the source of truth for rendering.** The Win32 editor's HD and 256x64 handling is
  to be treated as broken (confirmed by an author) and is never a reference for those.
- **Sprite matching always happens on the original ROM frame at native resolution**, never on an
  upscaled or extra plane. A plane smaller than the native frame makes no sense; libserum does not
  downscale.
- **The legacy source on this branch is stale.** The Win32 files in the repo root are 3.15.1.
  `master` is 3.17.3 (cROM header revision 20). Read legacy code with `git show master:<file>`.
- **Keep cROM/cRP as the edit format for now**; cROMc is generated by libserum. Once everything
  works the format may change and break 3.17.3 compatibility, but a loader for legacy projects
  must remain.
- **Deferred on purpose, do not optimise unasked:** memory use of large projects (saving a 450 MB
  project peaks at 2–3 GB) and save speed (cRZ compression is synchronous, about 6 s for 450 MB).
- **Commits:** intermediate steps are committed on `qt_rewrite_v2`, never pushed. In the sibling
  `libserum` repo commits carry no Claude co-author line and go to whichever branch the owner has
  checked out for the purpose.

## Architecture as it is now

- `core/` (Qt-free static library, links libserum):
  - `document/`: `ProjectDocument`, `ProjectSnapshot`, `EditorMetadata` (all cRP editor data).
  - `legacy/`: cROM/cRP parsers, `LegacyProjectSerializer` (writes complete files),
    `LegacyProjectFileWriter` (write beside, then rename; also writes the cRZ),
    `LegacyCrzArchive` (includes libserum headers).
  - `edit/`: `EditCommand` (all undoable commands), `UndoHistories` (scoped stacks with a global
    sequence for chronological undo), `DrawingTools`, `DrawingGeometry`, `FramePixelSelection`.
  - `render/`: `CanvasLayout`, `CanvasTypes`, `ProjectGeometry` (the one place that knows the
    plane layouts; `ProjectSnapshot` and `ProjectDocument` carry it).
  - `runtime/`: `RuntimePreview`, the libserum-backed renderer (the only other file that
    includes libserum headers). One instance per process, every call under one mutex, because
    libserum's state is process-global. `ProjectDocument::toSubsetSnapshot()` gives it a
    snapshot of the wanted frames and what they reference, with renumbered IDs, which the
    existing `writeLegacyCrom()` turns into a small cROM in memory. A still is: load that
    cROM, colorize once, dispose. A sequence keeps one cROM of several frames loaded.
    `ProjectDocument::revision()` changes with every edit and lets callers cache results.
- `app/`: `MainWindow` (about 4,600 lines, down from 8,266), `CanvasEditController`, the canvas and
  sprite editor widgets, `FrameImageUtils` (the editor's own preview renderer), `RuntimeView`
  (state of the canvas's Runtime view: on/off, plane, playback, cached libserum output),
  `LazyListIcons`
  (frame list thumbnails built for the rows in view), `PlaneLabels` (the one place that decides
  where the UI says "HD"/"SD" and what a single plane is called), seven panels under `panels/`.
- `tests/`: core test executable, widget test executable, `colorizing_qt_v2_roundtrip`
  (loads a real project, re-serializes, reports per block where it differs from disk; for a
  192x64 project differences in extra-plane blocks are reported as expected) and
  `colorizing_qt_v2_preview_diff` (renders every frame of a real project with the editor's
  renderer and with libserum and reports the differing pixels by class).
- `tools/ui_dump/`: offscreen harness that drives the real `MainWindow` through about 650 scripted
  states and dumps widget state, document contents and canvas hashes. Used to prove refactors
  change nothing and to review intended changes. Read its README before using it.

## What works

- Load and save of cROM/cRP/cRZ. Projects saved by 3.17.3 round-trip byte-identical: `afm_113b`,
  `trn_174h`, `hook_501`, `smb3`, and earlier `potc_600as`, GoT, `empty128`. `frankst1` (192x64)
  round-trips identical in every block of the original plane and in the cRP; its extra-plane
  blocks are rewritten, see "Resolution model".
- Save recomputes frame hashes and active-frame flags and blanks colorized pixels under dynamic
  masks, as the Win32 editor does. Header revision is kept (20 stays 20, older becomes 19).
- Editing: drawing tools, flood fill, palette gradients, canvas selection, comparison masks,
  dynamic masks/colours/shadows, backgrounds, sprites (capture, slots, detection areas, HD),
  palettes, colour rotations, frame settings, image import, PNG export, playback.
- Undo: scoped histories, chronological within a context, covers pixel edits, masks, dynamic
  colours and shadows, palettes, frame settings, HD create/remove for frames and sprites.
- 256x64-original projects: open, edit and save as native HD only (see below).
- 192x64-original projects: open, edit and save on the native 192x64 plane only (see below).
- Runtime view (`Edit -> Runtime View`, `Ctrl+R`): the canvas shows libserum's output for the
  current frame, 32-row or 64-row plane, read-only; playback through libserum with its color
  rotations; `Export Current Frame Runtime PNG...`. All three layouts.
- The editor's own renderer gives the same pixels as libserum on the plane with the ROM frame's
  size: `afm_113b` 3047/3047 frames, `trn_174h` 5211/5211, `hook_501` 3897/3897, `smb3`
  4430/4430, `frankst1` 303/303 sampled (`colorizing_qt_v2_preview_diff`). Before this step:
  `afm_113b` 4 frames differed, `smb3` 40, `trn_174h` 45.

## Resolution model

A project's `render::ProjectGeometry` is derived from the cROM header on load (original plane
size, extra plane size, the "256x64 original" flag) and written back on save. It says which
stored plane has the ROM frame's size ("native"), which planes are edited, and how plane pixels
map to ROM frame pixels. Exactly three layouts are accepted; any other size combination is
refused on load with a message naming the sizes.

`Resolution::Sd` and `Resolution::Hd` name the stored planes (original and extra), not sizes.

- **128x32 original, optional 256x64 HD** (ordinary projects): sprites and detection on the
  128x32 original; HD is the upscaled plane. Fully supported.
- **128x16 ROMs** are stored padded to 128x32 by the Win32 editor (`hook_501`); they are ordinary
  projects to the Qt editor. TXT import with padding is not implemented.
- **256x64 original** (`is256x64`, revision 20): the 256x64 plane is the only rendered plane, one
  to one with the ROM frame. Sprite originals, detection areas, slot bounds and capture selection
  are native coordinates. Stored SD data is carried through untouched and never shown. There is
  no SD mode and nothing can be removed from the 256x64 plane. A frame renders at runtime only
  if it, its background and all its sprites have their 256x64 data; the editor flags frames
  where that is not so and `Create 256x64 Frame` / `Create 256x64 Sprite` repair them.
  **Verified with synthetic projects only; no real 256x64 project exists yet** (authors were
  waiting for a better editor).
- **192x64 original** (stored as a 192x64 original plane with a 96x32 extra plane): the 192x64
  plane is the only plane shown and edited, one to one with the ROM frame; it is the stored
  original plane, so internally it is `Resolution::Sd` data. Masks, dynamic data, backgrounds,
  rotations, sprites, slot bounds, capture, import and export all use 192x64 coordinates.
  **The 96x32 data is discarded on load** (owner decision): `LegacySnapshotBuilder` and
  `ProjectDocument::fromSnapshot()` drop it, the document holds none (`Resolution::Hd` access
  throws), and a save writes the extra-plane blocks as "no extra data" through
  `document::discardExtraPlane()`: every extra flag 0, colorized frames, backgrounds, dynamic
  colors, shadows, rotations, sprite colors and sprite dynamic colors 0, dynamic masks, sprite
  masks and sprite dynamic masks 255, background masks 1. These are the values the Win32 editor
  gives a new frame, sprite or background without extra resolution (`CopyTXTFrames2Frame`,
  `AddTXTFrames2Frame`, add sprite, `AddBackground`). Block sizes and the header (192x64 with
  96x32) are unchanged; nothing is padded or converted. A second save is byte-identical to the
  first.
  **Verified with one real project (`frankst1`, which has no 96x32 pictures in use, no sprites
  and no backgrounds) and with synthetic projects** that have them. `frankst1` differs from its
  file in two extra-plane blocks after a load and save: `HD dynamic colors` (688808 of 2866944
  bytes; the file has values there) and `HD background masks` (all 34403328 bytes; the file has
  0, the editor writes 1). The Win32 editor has both values for an unused extra background mask:
  1 for frames added from a TXT dump, 0 when it converts an old-format file.

**"HD" and "SD" in the UI** are shown only for the ordinary layout, where HD is an extra
resolution. For the two single-plane layouts the SD/HD buttons, HD badges, the HD counter, the
`HD frames` filter, `(HD)` suffixes and `Remove HD` are hidden, and the plane is called `256x64`
or `192x64`. A 256x64 project keeps the marking of items that lack the data the runtime needs,
worded without "HD": `no picture` (badge, list lines, suffix), `not rendered` (status lines,
filter `Not rendered`), repair `Create 256x64 Frame` / `Create 256x64 Sprite`. A 192x64 project
has no Create or Remove button. Details and the full table are in the Handbook, "SD And HD
Modes".

## Open decisions (waiting for the owner)

1. **192x64: decided.** The 96x32 data is discarded on load and written as "no extra data";
   nothing is padded or converted to 256x64. Padding could be done in libserum later if it is
   ever needed. Still open inside that decision: which value an unused extra background mask
   gets. The editor writes 1 (what the Win32 editor gives new frames); `frankst1` has 0 there
   (what the Win32 editor writes when it converts an old-format file).
2. **Confirmations asked of the authors**, relayed by the owner, no answer recorded yet:
   - Sprite bounds fields are disabled for an empty slot, so a rectangle capture into an empty
     slot needs Assign or Select Capture first.
   - Switching monochrome off on a multi-selection clears the trigger only on frames that carry
     the monochrome trigger.
   - Undoing Create/Remove HD discards HD pixel edits made in between.
   - Frame settings cannot be undone while Dynamic mask mode is active.
3. **256x64 details:** the monochrome palette trigger in libserum now reads its palette from the
   HD dynamic colour set; a background repaired by `Create 256x64 Frame` becomes black.

## Known bugs and gaps in the editor (not fixed)

- Large projects still need a lot of memory while they are loaded and saved: opening `frankst1`
  peaks at 3.1 to 3.5 GB (the loaded file, the snapshot and the document exist side by side), its
  round trip at about 4.4 GB. Not optimised, see the ground rules. Open time is no longer an
  issue: frame list thumbnails are built for the rows in view, so `frankst1` opens in about
  2.7 s instead of 27 s and `trn_174h` in about 1.5 s instead of 5.3 s (release build, offscreen,
  M-series Mac), and the memory held after opening dropped from about 2.0 GB to 1.4 GB for
  `frankst1` and from 1.4 GB to 1.2 GB for `trn_174h`.
- The mask, background and sprite lists of the left sidebar still build every icon at once and
  rebuild all of them on many updates. Their counts are small, so this was left as it is.
- Error texts that come from `ProjectDocument` exceptions and reach the status bar were only
  partly reworded for single-plane projects ("256x64 frame is not available"); other core
  messages may still say "HD" there.
- **The editing canvas, thumbnails and the plain PNG export differ from libserum on the HD plane
  of an ordinary project** wherever the ROM frame decides what is shown. libserum renders that
  content at 128x32 with the SD dynamic masks and colours and upscales it (layer mode); the
  editor draws the HD dynamic masks and colours and doubles pixels. Measured on `trn_174h`:
  4249 of 5211 HD frames differ, 151384 pixels under dynamic masks (e.g. frames 527, 1157), 782
  pixels at sprite edges (e.g. frames 1455, 697). Frames without HD have no 64-row picture in
  the editor at all. The Runtime view shows the real picture in all these cases. Not
  reproduced on purpose: the upscaling. Open: whether HD mode should show what libserum does
  with the HD dynamic mask, which is nothing.
- In a 256x64 project a frame whose background or sprite lacks 256x64 data is drawn without it
  by the editing canvas (to stay editable); libserum shows nothing for the frame.
- Runtime view: no `.pup.csv` scenes and no `scaling.txt` (libserum's memory load reads neither,
  so the 64-row plane always uses the default Scale2x and shadow offset); a frame is rendered
  from a cROM of that frame alone, so which of several frames with the same hash a machine
  would pick is not shown; runtime playback loads at most 48 frames at a time and starts
  libserum's state afresh for the next 48; the trigger libserum reports is not shown.
- Runtime render cost per frame (subset, serialize, load, colorize; release build, M-series
  Mac): `hook_501` 0.24 ms, `afm_113b` 0.60 ms, `trn_174h` 1.8 ms, `smb3` 2.1 ms, `frankst1`
  2.0 ms mean; the load is 70 to 90 percent of it. Frames with many sprites cost about 10 ms
  (`smb3` frames 2200 to 2700, 3.8 MB cROM each). The view renders at paint time and only when
  the document revision, the frame or the plane changed, so repaints are free and bursts of
  changes coalesce; no timer and no thread.
- 16-colour originals show only 4 shades in the reference view (`value & 3`).
- The Selection tool paints in mask and capture modes instead of selecting.
- "on N frame(s)" status texts count skipped frames.
- Not undoable: sprite slot assign/remove/bounds, detection areas, names, sprite capture, colour
  rotations.
- Sprite capture does not record the source frame, rectangle and mirror flags in the cRP, and
  leaves the sprite's old dynamic mask in place.
- New frames from `createEmpty` are not a complete new-project path; there is no "new project".
- Windows and Linux builds are untested (only macOS arm64). The ui_dump private-access trick is
  not expected to link with MSVC.

## Feature parity still missing against 3.17.3

- New project and "add frames" from a TXT dump, with the import filter and dedupe.
- Frame delete (selected, by duration, same frames), same-frame lists, "spot common".
- Add and delete sprites, backgrounds and comparison masks (the serializer supports changing
  counts; the document and UI do not yet).
- Sections (list, add, rename, delete, reorder) and the trigger list. The data is loaded and
  saved, there is no UI.
- Copy/paste, auto copy, scrolling auto fill, selection helpers, mirror.
- Colour sets, edit colours, colour picker dialog, colour-set replace drawing mode.
- Sprite dynamic masks and colours, sprite shape mode (data modelled, no UI).
- Auto shadow, brightness, black and white, Dyn>Stat, "to source frame".
- Selectable resize filters for HD creation.
- Images window: video import, crop zones, scroll copy.
- Animated GIF export.
- Frame tester (dump playback through libserum, next unidentified, search frame by ID), ZeDMD
  output, PuP tester. Playback of the project's own frames through libserum exists (Runtime
  view).
- Autosave and recovery.
- cROMc export through libserum.

## Next steps, in the order I would take them

1. Confirm the value written for an unused 192x64 extra background mask (open decision 1) and
   check a 192x64 project saved by this editor on a real machine.
2. Decide what HD mode shows for dynamic content (see "Known bugs and gaps"), and whether
   thumbnails and the plain PNG export should come from libserum. Measured: a runtime render
   costs 0.2 to 2 ms against 0.05 to 0.13 ms for the editor's renderer, and on the native plane
   the two are pixel-identical on all five real projects, so thumbnails gain nothing from it;
   the export can simply be the runtime export.
3. Build the frame tester on `RuntimePreview`'s sequence mode (feed a TXT dump, next
   unidentified frame, search by ID), and load `.pup.csv`/`scaling.txt` for it if libserum gets
   a way to pass them from memory.
4. Fix the remaining editor bugs listed above.
5. Continue shrinking `MainWindow`: toolbar and tool state, frame list and playback, file
   handling.
6. Feature parity, most used first: add/delete of frames, sprites and backgrounds; sections and
   triggers; copy/paste; TXT import.
7. Later, by decision of the owner: memory use, save speed, a new project format.

## libserum work done in this effort

- `Serum_CRZ_Read`, `Serum_CRZ_Free`, `Serum_CRZ_GetEntryName`, `Serum_CRZ_WriteFromFile`.
- Native rendering of `is256x64` projects on the 256x64 plane only; before, everything except
  frame identification read the 256x64 ROM frame as 128x32.
- Sprite regression in 2.8.0 (introduced with the `upscale_layers` squash, 2026-09-06): with a
  64-row-only request, sprites without HD art were not drawn; with both planes, sprites that moved
  or disappeared stayed on the 64-row plane. Fixed in `c584161`.
- A 64-row plane painted by the monochrome fallback was kept for the next identified frame.
  Fixed in `789f410`.
- `9ac0511`: internal decoder helpers moved into their own source file; debug-only hashes are
  computed only when a debug switch asks for them. Output is bit-identical.
- `Serum_LoadFromMemory(crom, size, flags)`: loads a raw cROM from a caller-owned buffer through
  the same load sequence as `Serum_Load()`; reads and writes no file. Uncommitted working-tree
  change in `../libserum`, which the editor now needs.
- Not touched and not testable on a Mac: everything behind `is_real_machine()`.

## How to build and check

```sh
cmake -S qt_rewrite_v2 -B <build dir> -G Ninja -DCMAKE_PREFIX_PATH=/opt/homebrew/opt/qt
cmake --build <build dir>
(cd <build dir> && QT_QPA_PLATFORM=offscreen ctest --output-on-failure)
<build dir>/tests/colorizing_qt_v2_roundtrip <project>.cRZ <project>.cRP   # must print "identical" twice
<build dir>/tests/colorizing_qt_v2_preview_diff <project>.cRZ <project>.cRP   # native plane identical
qt_rewrite_v2/tools/ui_dump/run.sh baseline   # before a change
qt_rewrite_v2/tools/ui_dump/run.sh after      # after it
```

The build is warning-free with `-Wall -Wextra` and must stay so.
